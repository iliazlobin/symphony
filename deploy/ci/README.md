# Private Linux CI

The repository-scoped `symphony-linux` scale set runs Linux CI on private GKE nodes. [ARC](https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/deploy-runner-scale-sets) creates a new gVisor Pod for each job and removes it afterward. GitHub still stores workflow logs, artifacts and caches; this public repository's [workflow logs and artifacts remain readable](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs) by users with repository read access. This bootstrap package adds an opt-in smoke workflow; the required `make-all` and `validate-pr-description` checks stay on their existing runners until the private pilot is verified.

## Public repository admission

- Before registering runners, set GitHub's [fork approval policy](https://docs.github.com/en/rest/actions/permissions#set-fork-pr-contributor-approval-permissions-for-a-repository) to `all_external_contributors`. The installer reads that policy through the operator's existing `gh` authentication and stops on a missing, weaker or unverifiable policy before any Kubernetes or Helm operation. Keep the policy enabled while the scale set is registered; this install-time check does not monitor later settings changes.
- A fork can change workflow YAML or add a job targeting `symphony-linux`. Routing same-repository PRs to GKE and fork/Dependabot PRs to `ubuntu-latest` keeps the normal required checks running, but is **not an access boundary**. Before [approving any external workflow run](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks), inspect the current head's workflow files, including added jobs and reusable workflows; do not approve an external run that targets private/self-hosted runners. Do not use `pull_request_target` to execute an untrusted PR head. This personal repository has no organization-level [runner-group workflow restrictions](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access), so admission depends on this maintainer review as well as the job isolation below.
- The smoke workflow accepts only [`workflow_dispatch`](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), which requires repository write access. Dispatch the reviewed default-branch revision; selecting an arbitrary branch is not a trust check. Keep App and operator credentials outside jobs, and keep job tokens read-only. If these approval controls cannot be maintained, drain the scale set rather than relying on workflow routing alone.

## Resources and isolation

- `gcp-foundation` owns the shared private `platform-ci` gVisor node pool and cluster-wide ARC CRDs in `iz27-platform-dev/platform-dev`, `us-west1-a`. The pool starts at zero and is capped at one 4-vCPU node. Symphony and Events Concierge share node capacity; each owns its separate namespaces, registration, image and repository-only App. This package does not resize `shared-dev`, activate the coding pool, deploy applications or change their state.
- This repository owns `symphony-ci-system` for the ARC controller/listener and `symphony-ci-runners` for job Pods. The controller watches only the latter namespace; the job service account has no role bindings, token mount or cloud identity. Controller and listener request 150m CPU in total on `shared-dev`; job Pods select `platform-ci`. No App credential, job home or repository image is shared with Events Concierge.
- Each repository has `minRunners: 0`, `maxRunners: 1` and a one-Pod quota. Symphony jobs request 2 CPU and 6 GiB memory. On the sole shared node with less than 4000m allocatable CPU, two 2-CPU jobs cannot run together; verify that capacity after pool creation and retain these requests. Both repositories can have an assigned Pod pending capacity; Kubernetes scheduling gives no cross-repository FIFO or fairness guarantee. Zero retained storage bounds each job. Each job gets disposable runner home, checkout and temporary files. A [minimal init process](https://github.com/krallin/tini#subreaping) reaps orphaned children; both the image and Pod command invoke it. The image runs as UID 1001, with read-only root, no additional capabilities, no privilege escalation, no Docker/socket/container hooks and no model authentication.
- Network policies deny incoming traffic and allow DNS plus public IPv4 TCP 443. Private networks, Kubernetes API and link-local metadata remain denied to jobs. This is a public-HTTPS port policy, **not a hostname allowlist**; arbitrary public HTTPS is reachable. GitHub, Hex, npm and PyPI need outbound access. DNS selectors and the pinned addresses must match the actual cluster.
- The GitHub App is installed only on `iliazlobin/symphony`, with repository Administration read/write and Metadata read. Its private key lives in the pre-created `symphony-ci-github-app` Secret in the runner namespace, as [required by the chart](https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/authenticate-to-the-api). ARC's trusted controller also creates a listener configuration Secret in its own namespace. Job Pods receive only their short-lived ARC JIT registration, never the App key. Keep both namespaces free of application credentials; do not grant job RBAC or mount the source Secret.
- GKE workload logging retains controller/listener and runner output after ephemeral Pod removal. Confirm collection and retention in the deployed project. Job and Pod deadlines bound execution; a stalled scale-set registration, quota denial or exhausted node capacity leaves work queued rather than increasing limits.

## Build and install

Use the existing platform [private access runbook](https://github.com/iliazlobin/gcp-foundation/blob/main/README.md) and verify the account, project, private cluster and approved platform plan. Deploy only after source review/checks and the bounded pool setup. Preserve the existing remote Terraform state and application resources.

Build the committed [Dockerfile](Dockerfile) for Linux amd64. It pins the existing Elixir 1.19.5/OTP 28 image, official runner 2.337.0 checksum and Node 22.14.0 checksum. Publish to the existing private repository and record the resulting immutable digest and source revision in the PR/deployment evidence; tags are not deployment pins.

```sh
ci_revision=$(git rev-parse HEAD)
docker buildx build --platform linux/amd64 --build-arg SOURCE_REVISION="$ci_revision" \
  -f deploy/ci/Dockerfile -t "us-west1-docker.pkg.dev/iz27-platform-dev/symphony/ci-runner:$ci_revision" \
  --push .
```

For local amd64 validation on Apple Silicon, [Elixir documents an Erlang JIT emulation workaround](https://hexdocs.pm/mix/Mix.Tasks.Release.html#using-images): pass `ERL_AFLAGS='+JMsingle true'` to the disposable test container only. Give its temporary filesystem execute permission to match GKE's disk-backed `emptyDir`. This local workaround is not baked into the native GKE image; local results do not replace the native pilot below.

Create the dedicated GitHub App and install it only on this repository. The planned Secret Manager home is `projects/iz27-platform-dev/secrets/symphony-ci-github-app`; retain one JSON payload with `github_app_id`, `github_app_installation_id` and `github_app_private_key`. After reviewed source and platform setup are approved, run the guarded `--prepare` mode below to create only the two CI namespaces and their restrictions; it verifies every admission/CRD prerequisite and stops before reading a Secret or installing controllers. Deliver those fields to `symphony-ci-runners/symphony-ci-github-app` over a private operator channel; keep values out of Git, Terraform, command arguments, logs and Helm values. Do not reuse a personal GitHub token, Codex home, model authentication volume or application credential. Verify the installed repository and App permissions without printing credentials.

Put `gh`, `kubectl` and `helm` on the operator's PATH, verify that `gh` can read this repository's Actions approval policy, and set `KUBECONFIG` to the task's private access file. Review [foundation.yaml](foundation.yaml), [controller-values.yaml](controller-values.yaml), [runner-values.yaml](runner-values.yaml) and [versions.json](versions.json). The install helper verifies external-contributor approval, the context, API/DNS service addresses and downloaded chart checksums before applying CI resources. It also requires all four shared CRDs to be established and match the pinned chart exactly, including schemas, served/storage versions and stored versions; only API defaults for `conversion: {strategy: None}` and `preserveUnknownFields: false` are normalized. Missing or different CRDs stop installation before any mutation; resolve them through the platform owner. It accepts only the private registry's reviewed digest and supplies it to both init and runner containers; the source placeholder cannot be deployed through this helper.

Before either mode, read current `shared-dev` allocation with `kubectl describe nodes -l cloud.google.com/gke-nodepool=shared-dev`. Remaining CPU requests must fit 300m and memory requests 512Mi for both controller/listener pairs, minus only their already-installed Pods in the two trusted CI system namespaces. Confirm ownership and names rather than excluding arbitrary labeled Pods. Recheck before each install; if capacity is insufficient, stop without reducing requests or resizing the pool. The reviewed placement leaves little CPU headroom. The pinned chart has no rollout-strategy value, so the installer uses a checked post-renderer to set only its exact controller Deployment to `Recreate`; upgrades need no overlapping controller Pod. Listener drift deletes the prior Pod before its same-name replacement. Drain jobs and verify old control Pods are gone during maintenance.

```sh
deploy/ci/install.sh --prepare
# Deliver the repository-only App Secret through the approved private operator channel.
deploy/ci/install.sh 'us-west1-docker.pkg.dev/iz27-platform-dev/symphony/ci-runner@sha256:<reviewed-digest>'
```

ARC 0.15.0 is pinned by both OCI and archive digests. The controller image is also pinned by digest. Foundation installs the shared CRDs once; both repository Helm releases use `--skip-crds`. [Helm does not upgrade CRDs](https://helm.sh/docs/chart_best_practices/custom_resource_definitions/), so a second controller install is not evidence of schema compatibility. Coordinate CRD/controller upgrades across repositories through foundation, inspect schema and stored-version changes, and follow [ARC's upgrade procedure](https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/deploy-runner-scale-sets#upgrading-arc). Never replace, downgrade or delete shared CRDs from this installer. Rotate the runner image when GitHub requires/security updates it; rebuild and reverify the same boundaries.

## Verify and operate

1. Confirm the single `platform-ci` node has less than 4000m allocatable CPU and jobs retain their 2-CPU requests; this verifies the shared one-running-job bound. Confirm controller and listener are Running on `shared-dev`, no idle runners, and the scale set's repository URL/name/max/min. Inspect rendered Helm roles: the controller may manage CI resources only; the job service account must not have secret, Pod, exec or cloud access.
2. After the bootstrap workflow is merged to the default branch, start the [private-ci-smoke workflow](../../.github/workflows/private-ci-smoke.yml) on the reviewed revision. The first job verifies the actual tools, UID, capability restrictions, absent privileged paths, DNS/HTTPS and denied API/metadata, then leaves a file. The second job repeats the checks and requires that file to be absent. Check distinct runner names and Pod UIDs, the exact image digest, gVisor RuntimeClass, protected `platform-ci` node selector/taints, absence of SA token/App key mounts, and removal of both runners/Pods. The workflow's checks are not independent Pod admission evidence; inspect the actual Pod manifests from the operator API.
3. After Symphony drains, verify zero Symphony runner Pods and registrations. The shared pool can return to zero only after both repositories have no queued, pending or running work; then verify its managed instance-group target returns to zero. Autoscaler removal is delayed; do not delete a running node to claim cleanup. Confirm application/coding workloads and retained volumes are unchanged.
4. Open a separate routing PR for the two required jobs: use `symphony-linux` for pushes to `main` and same-repository PR heads from trusted writers; route fork and Dependabot PRs to `ubuntu-latest`. Retain the job names, triggers and full `make all`, Python and asset checks on both paths; never skip an untrusted job into a successful required check. Keep mise tool setup and existing cache steps only on hosted runners. On GKE, use the image's pinned tools, direct `npm` commands and `python3 deploy/ci/probe_runner.py`; the probe's UID and filesystem checks do not apply to hosted runners. Set `permissions: contents: read`, checkout `persist-credentials: false`, bounded timeouts and PR-description temporary files under `RUNNER_TEMP`. Require real executions of both routing paths, cold GKE compilation timing/memory evidence, independent Copilot review and all checks before merging this routing change. A timeout or failed check remains a failure; preserve branch protection and human task acceptance.

Use `kubectl -n symphony-ci-system logs deployment/symphony-ci-controller`, `kubectl -n symphony-ci-system get pods` and `kubectl -n symphony-ci-runners get pods,events` for failure diagnosis; logs can contain job code output and must remain private. Preserve failed check evidence. For maintenance, set both Helm `minRunners` and `maxRunners` to zero, wait for active work and runner cleanup, then update only the reviewed CI release. A rollback uses the prior image/chart digests; never delete namespaces, credentials or retained application resources as cleanup.

Linux CI activation does not make every workflow private. [Release verification](../../.github/workflows/burrito-release.yml) still includes native macOS and Linux ARM checks on their existing runners. Migrate them only after private runners for those architectures exist and pass the same tests; do not remove or relabel their evidence. Repository billing/service holds may prevent dispatch before a runner is assigned even when GKE is healthy.
